- [ ] **bitmap-and-reads-both-payloads-in-full** ( *2026-09-18, from chasing whether `bitmap x bitmap` is too slow* ): `and_cardinality` on two bitmap containers reads both 8 KiB payloads whatever their density, because a dense AND must. At ~98 ns for 16 KiB it is **167 GB/s, ~43 B/cycle**, which is ~89% of a 3-load/cycle ceiling -- so the kernel is load-bound and **at most 1.1-1.5x** remains.

  **Four kernel-level attempts to claim it all failed** and are recorded in JOURNAL so they are not repeated: Harley-Seal CSA **0.35x**, paired 32-byte loads **0.68x**, deferred widening **0.83x**, and **ARM SVE -- inapplicable twice over**. Counting is not the bottleneck on NEON, so every technique that trades dependency chains for fewer `cnt` operations loses.

  **Check SVE before re-trying it, in one command.** `libpopcnt` advertises an SVE popcount beating its NEON one, qualified *"especially on CPUs whose SVE vector width is larger than NEON's 128 bits"*. On this Cortex-X925 `cat /proc/sys/abi/sve_default_vector_length` is **16 bytes -- exactly NEON's width** -- so a load-bound kernel gains nothing; and the intrinsics are `stdarch_aarch64_sve`, **nightly-only**, against this crate's stable MSRV 1.89. Re-open only where that file reads above 16 *and* the intrinsics have stabilized.

  **The literature agrees, including the author of the losing technique.** Muła, Kurz and Lemire ( arXiv:1611.07612 ) is the canonical AVX2 Harley-Seal result -- 2x over `popcnt`, 2.4x for two-bitset similarity -- and Muła's own `sse-popcount` publishes aarch64 numbers where plain CNT beats Harley-Seal at **every** size by ~1.5x. `libpopcnt` copies Harley-Seal from that repo **for AVX2 only**.

  **So the remaining win is a format question, not a SIMD one.** The measured operands were sparse -- 16 535 bits across 131 072 -- and nothing lets the intersection skip regions known to be zero on one side. A summary layer ( a per-region occupancy word, or promoting sparse payloads out of `Bitmap` sooner ) would beat any kernel tuning available here. Note the counter-pressure before opening it: this crate's whole point is that container choice is already density-driven, so a bitmap holding 16 535 of 65 536 values is **within** the range `BITMAP_DEMOTE` deliberately keeps as a bitmap, and changing that is a demotion-threshold decision with its own measurements. -- *source: JOURNAL `2026-09-18 -- three ways not to speed up ops::bitmap's NEON kernel`*

- [ ] **simd-arms-without-a-crate-level-case** ( *2026-09-18; **audited and largely retracted the same day -- see the audit note at the end** -- the figures this entry was opened over came from a probe with a hoistable timing loop* ): `ops::mixed` and `ops::run` have x86 arms that are **correct but not shown to pay**. Measured on an Intel i9-9880H by alternating two binaries built against the real API: `ops::mixed` disabled alone moves `array x run` by **1.00x**, and `ops::run` gives **1.10x** against a 3.4% spread. Compare `ops::bitmap` at **2.51x** and `ops::array` at up to **8.51x**, both unambiguous.

  **CORRECTED 2026-09-18, within the hour, and the correction is the point.** The `1.00x` for `ops::mixed` was not the kernel win being absorbed by the container path. **The arm was never called.** `and_cardinality( array, run )` is a scalar two-pointer written in `ops::card`; `simd::filter_by_run` is reached only from `merge_array_run`, which returns a `Vec<u16>` and so serves **apply**. The probe timed a path the arm is not on and reported the result as a property of the arm.

  Two gates stand before that arm runs, and a measurement must clear **both**: the operation has to be the container-producing one, and `vals / nruns` must be below `RUN_SEEK_RATIO` ( 256 ) or the seek path answers it first. Clearing neither yields `1.00x`, which reads exactly like a finding.

  So `ops::mixed`'s crate-level value is **unmeasured**, not measured-as-zero, and `ops::run`'s 1.10x needs the same audit before it is trusted -- `run x run` cardinality may or may not reach `block_and_cardinality`. **This is not a request to delete either arm.** They carry their bounds, they are sabotage-verified, they cost nothing when skipped, and their kernels are faster in isolation ( the AVX2 popcount is 2.70x ).

  The transferable lesson is about instruments, not SIMD: **a null result from a benchmark that never executed the code under test is indistinguishable from a null result that did**, and nothing in the output says which you have. The check that would have caught it in seconds is the one used everywhere else in this tree -- sabotage the kernel and confirm the benchmark *moves* before believing a number it reports.

  **AUDITED 2026-09-18. The instrument was the bug, and four figures are withdrawn.** The probe's timing loop black-boxed the *result* and not the operands, leaving the call loop-invariant, pure and hoistable -- so whether it was timed at all depended on inlining in unrelated modules. Fixing that exposed a second problem: `bitmap x bitmap` is **bimodal** in the harness, ~102 ns or ~290 ns from the same binary ( eight consecutive runs: 101.7 seven times, 290.1 once ).

  What survives is what shows **single-module response** -- moves when one arm is disabled and only that one:

  ```text
    run x run        132.6 -> 238.7 ns   ops::run only      1.80x
    array x bitmap  1637.4 -> 1907.5 ns  ops::bitmap only   1.17x
  ```

  `ops::bitmap`'s 2.51x and `ops::run`'s 1.10x are withdrawn from the module headers ( the latter *understated* the arm by half ). `ops::mixed` is **unmeasured**, not measured-as-zero. `ops::array`'s 8.51x stands -- criterion, and monotonic in `m`, which a hoisted loop is not.

  **The standing rule this produced**: before any speedup figure goes in a header, disable the kernel and confirm the benchmark moves *and moves for that kernel alone*. Sabotage-verification was applied to every correctness claim that day and to no performance claim; that was the entire gap.

  Note the trap that nearly turned this into a false regression report. `array x run` first measured **0.81x**, looking like the mixed arm making things 24% slower. Per-module isolation showed it at 7270 ns all-on, 5534 ns with `ops::array` off and 5981 ns with `ops::bitmap` off -- two unrelated modules each "improving" it by a fifth. That is **code layout sensitivity**, not a causal effect, and any figure for this path has to be treated as measuring which binary was built. Do not quote `array x run` timings without the per-module control. -- *source: JOURNAL `2026-09-18 -- three more x86 arms`*

- [ ] **mysql-write-row-cannot-batch**: `yesno-mysql`'s embedded backend writes one ordinal per commit, so the C ABI's dispatcher has nothing to fan out to -- one ordinal is one shard is one task. - [ ] **mysql-records-in-range-is-whole-key** ( *2026-09-18, found auditing the driver boundaries* ): `ha_yesno::records_in_range` answers a **point** lookup exactly -- `HA_READ_KEY_EXACT` with no upper key resolves through `Backend::Contains` -- and every other range falls through to `records()`, which is `Backend::Cardinality`, the total for the key.   Not a wrong answer ( estimates are hints ), but yesno computes exactly this cheaply: `len_in_range` and `range_summary` answer complete chunks from index cardinalities without reading a payload, and the PostgreSQL FDW already gets the benefit through Flight pushdown.

- [ ] **decoded-geometry-does-not-drive-address-calculation** ( *renamed and narrowed 2026-09-12 from `stored-superblock-descriptors-are-not-authoritative`, whose correctness half is closed* ): the allocator's capacity, slot lookup and new-allocation arithmetic use the **compiled** size-class ladder, page size and slab size rather than the ones decoded from the superblock. **This is no longer a correctness gap, and that is the change.** `SuperBlock::decode` refuses a file whose `class_sizes`, `page_size` or `slab_size` differ from this build's, and `superblock::pick` — the **only** production read path, called from both store-open sites — decodes both slots and propagates that error. So no address calculation can ever run against a geometry the compiled constants disagree with: the allocator reading compiled values is safe because a file carrying anything else never opens. A zero in `page_size` or `slab_size` is tolerated as a pre-comparison file written at the compiled value, following the `node_size` precedent; `shard_id` deliberately gets no such tolerance, because shard 0's number *is* zero and tolerating it would re-open the image-swap hole for every pair involving shard 0.

**Why a decode-level test is sufficient here, unlike for `check_identity`.** That method was a *separate* check a call site had to remember, and it sat with no caller for part of a session — this repository's most-repeated failure class. The geometry comparison lives **inside the decoder**, so there is no second wiring step to forget: nothing can open a shard without decoding its superblock. That is the distinction to apply before demanding an end-to-end test for a validation — ask whether the check can be reached without being called, not merely whether an integration test exists.

**What remains is a capability, not a fix**, and it is gated on a workload: thread one decoded geometry object through capacity, slot lookup and allocation so a non-default ladder can be *honoured* rather than refused, plus a non-default-ladder round-trip test. Do not start it to make the format "properly versioned" — no file the crate has ever written carries a non-default geometry, so today the fields buy a clear refusal at zero cost, which is the honest state until someone needs to retune.

### PostgreSQL extension

- [ ] **fdw-two-phase-commit**: `yesno-pg` buffers writes per transaction and flushes them in a `XACT_EVENT_PRE_COMMIT` callback, so `ROLLBACK` is correct and a multi-row statement costs one server commit. A crash **between** that flush and PostgreSQL's own commit record leaves the two disagreeing: yesno has the rows, PostgreSQL does not. There is no `PREPARE` implementation and no claim of one.

  Closing it means implementing the two-phase callbacks against a durable yesno prepare/resolve protocol, which yesno does not currently expose. A prepared `WriteBatch` cannot merely reserve an ordinary commit version: the unresolved slot is a hole in the consecutive-prefix visibility oracle and would stop every later commit becoming visible for as long as PostgreSQL leaves the transaction prepared. A sound design needs durable prepared operations outside that ordered stream, idempotent commit/discard RPCs, and restart reconciliation with PostgreSQL's transaction status before assigning the real yesno version. Worth weighing against just documenting the window: the FDW's writes are an ingest path, and an ingest that occasionally re-sends a batch is idempotent here, because a set holds each ordinal at most once. -- *source: phase 5, 2026-08-29; design audit 2026-08-30*

- [x] **fdw-savepoints-are-not-honoured** ( *found 2026-09-18 auditing transaction boundaries; falsifier landed red the same day; **FIXED 2026-09-19**, `gate-pg passed` on both majors* ): `yesno-pg` buffered writes per transaction in a thread-local and registered **`RegisterXactCallback` only**. PostgreSQL delivers subtransaction aborts exclusively through `RegisterSubXactCallback` -- `XACT_EVENT_ABORT` fires at top level and nowhere else -- so nothing discarded writes made after a savepoint that was rolled back, and the same buffer feeding the read overlay showed them to the transaction that had rolled them back. It fired with no `SAVEPOINT` in the text too: a PL/pgSQL block with an `EXCEPTION` clause opens an implicit subtransaction.

  **It was data loss as well as spurious rows.** A `DELETE` issued inside a savepoint and rolled back was still applied at commit, so a row the user had restored disappeared. Measured before the fix: `INSERT 10, 20; SAVEPOINT s; DELETE 10; ROLLBACK TO s` left `20`.

  **The fix is a stack of per-level maps** in `fdw/modify.rs`, keyed by `GetCurrentTransactionNestLevel()`, with a subtransaction callback beside the transaction one. `ROLLBACK TO` drops every level at or below the ending one and the parent's entries are untouched -- which is what restores the deleted row; `RELEASE` merges the level into its parent with the deeper verdict winning. Reads and the flush both flatten ascending, so a transaction cannot see or commit what it rolled back.

  **Do not narrow the handlers to the exact ending depth.** They are written as "at or below" on purpose: `ROLLBACK TO` an outer savepoint aborts every level from the innermost down to and including the named one, and the level whose rollback re-establishes it must be usable again afterwards. `discarding_an_outer_level_takes_every_level_inside_it` is the unit test that catches the narrowing, sabotage-verified.

  **Why not tag entries with the subtransaction that wrote them**: the per-ordinal map is last-write-wins, so an ordinal inserted by the parent and deleted by the child has already lost the parent's verdict by the time the rollback arrives. The stack is what preserves it.

  Coverage: `e2e/postgresql/{sql,expected}/fdw_savepoint.sql/.out` ( seven cases: rollback-to, release, the rolled-back `DELETE`, nested savepoints, a PL/pgSQL `EXCEPTION` block, rollback to a non-innermost savepoint with a re-established level and a repeated rollback to the same name, and release of an outer savepoint carrying a nested one ), plus eight pure `#[test]`s on the stack algebra in `fdw/modify.rs` run by `//yesno-pg:unit`. The expected file was written from PostgreSQL's semantics rather than from output, and it failed six ways before the fix. -- *source: transaction-boundary audit of `yesno-pg/src/fdw/modify.rs`*

**AUDIT 2026-09-13 — every citation in the proposal was checked against the tree and they hold**, including the two long quotations ( `formal-model.md:2071-2077`, `bignum/mod.rs:1-8` ), the `Reduce::keep` body, `Backing::Paged`'s "no leaf reports this yet" doc, and all four of the §7 gaps. They do not change the verdict above -- accept the framing, hold the implementation -- but four of them must be applied before any of it is written, and the fifth is a one-line fix worth doing now.**

1. **`Slice::sub` must wrap, not saturate, and the proposal's appeal to precedent is wrong twice.** §4 gives the signature as "saturating at zero, as bignum does". `bignum/addsub.rs:12` says flatly "**There is no saturating arithmetic and there will not be**", and `BigUint::sub` returns `Option<BigUint>`, refusing on underflow rather than clamping. The decisive argument in that module header transposes onto a slice exactly: the reader cannot saturate, because reading integer `k` at `width_bits = W` gathers only `[k*stride, k*stride + W)` and is therefore `x mod 2^W` **by construction**. A slice's `value_at( o )` reads `L` planes and is `mod 2^L` for the same reason, so truncation is again the only write rule that agrees with the read rule. A slice cannot borrow `bignum`'s `Option` refusal either, since subtraction is elementwise over `N` ordinals at once -- the honest signature wraps and says so, or returns the borrow-out plane as a mask. **This is the one place the proposal contradicts the doctrine it otherwise honours, and its own §1.3 transpose argument is the tool that catches it.**

2. **`ops::csa` must return `( Option<Container>, Option<Container> )`.** Every shipped kernel -- `ops::{and, or, xor, and_not}` over `ops::apply` -- returns `Option<Container>`, with `None` meaning the empty result. The proposal's `-> ( Container, Container )` would make `csa` the only member of the family that materializes an empty container. This is not cosmetic: in `add_many` over sparse addends a `None` carry **is** the early exit that §4's second bullet spends a paragraph on, so putting it in the return type makes that guard free instead of "close to dead code at chunk width".

3. **The §4 speed ratios are inflated roughly 1.5x by asymmetric operation counting, and the correct numbers should go into the benchmark as the expectation.** Fused CSA at 5 word operations is right ( `t = a^b`, `sum = t^c`, `a&b`, `c&t`, `or` ). But the "obvious ripple-carry" baseline for adding a **one-bit** addend into an `L`-plane accumulator is a half-adder ripple -- `new_carry = acc[j] & carry; acc[j] ^= carry` -- which is **2 operations per plane, so `2nL`, not `3nL`**. The ratio is therefore `2L/5 = 0.4L`: **3.2x at `L = 8` and 4.0x at `L = 10`**, not the 4.8x and 6.0x quoted. The win is still real and still worth the kernel. Carrying the inflated pair into `haiiie`'s benchmark is how an honest result gets read as a regression when it lands. Note also that §2 already has the better argument and §4 does not reuse it: at container granularity the word-operation count is the wrong model outright, because allocation, cardinality counting, kind dispatch and the demotion check dominate. **Five passes and three throwaway containers against one pass and none is the claim to benchmark; `5n` against `2nL` is a lane-level sanity check, not the case.**

4. **§1.2's "the encoding stays where the document put it" is doing more work than it admits, and amending `formal-model.md` is an unlisted cost.** A caller bit-slicing a rating column into four planes is performing O'Neil-Quass bit-slice encoding. The proposal's dodge -- that yesno does not do the encoding, the caller assigns the keys, and each key is still one equality-encoded set -- is honest, but the consequence is that yesno would ship the **arithmetic** for an encoding it declines to own, while `formal-model.md:2071-2077` currently reads as though yesno has nothing on that axis at all. That paragraph would need an amendment in the same change, and §8's sequencing does not list it.

5. **The space consequence of a slice is analysed in §4 and then not drawn.** The early-exit bullet correctly observes that at density ~ 0.5 no carry plane is empty below `j` ~ 16. The unstated corollary is that those planes are bitmap containers throughout, so a slice over a `10^9`-ordinal universe at `L = 10` is ~1.25 GB -- and `add_many` over `10^9` ordinals is the headline claim. For the faceted-search caller the addends are sparse and this never bites. Both regimes should be named rather than one.

That is false for a memtable-resident `BitStore::Mut`, where `to_boolean_buffer` ( `buffer.rs:232` ) re-encodes 8 KiB byte by byte. The proposal files the behaviour as a missing API; the wrong doc comment is a one-line fix that stands on its own. **AUDIT ADDENDUM 2026-09-13 -- a sixth correction, and the largest: `slice` would be the first lens ever wired into the expression surface.** Raised by a reader's question, not by the audit. **`Expr` and `ChunkStream` appear zero times in `bignum/`, `matrix/`, `view/` and `pack/`** -- all three shipped lenses are strictly eager, taking an `OrdSet` and returning an `OrdSet`, a `BigUint`, a `BitMatrix` or a scalar, and none has ever touched the lazy surface. §5's `ge( t ) -> Expr` and `top_k( within: &Expr, k )` are therefore **not** covered by §1.3's "it is the transpose of a lens that already ships": the transpose argument licenses the *arithmetic* and says nothing about API shape. The asymmetry is probably **right** -- `top_k`'s entire economy is `L` cardinality evaluations materializing nothing, and an eager `ge` would materialize a set per plane, which is the cost the operation exists to avoid -- but it should be argued rather than smuggled. It makes the filing two proposals: bit-sliced arithmetic over sets, which fits the existing eager doctrine, and **the first wiring of a lens into lazy evaluation**, which is a much larger architectural commitment currently riding on the first one's argument. Three consequences: the decision actually lands at §8's **step 3** ( `ge` ), not step 4 ( `top_k` ) where the payoff is; **`ge` needs no new `Expr` variant** and so is far cheaper than it looks, because a descending compare-with-borrow is a boolean formula over the plane sets and lowers to the existing `And` / `Or` / `AndNot` / `Not` over `Expr::Set` leaves -- **verify that before writing anything**, since a `ge` needing a new variant is a different proposal again ( `Expr` is matched exhaustively in `open_planned`, `flatten_or` and the planner ); and `top_k` re-opens its expression `L` times with a tied-set tree that deepens per plane, so materializing `tied` as an `OrdSet` each step is the obvious alternative and should be measured rather than assumed away. `view_count` ( §3 ) is unaffected and stays eager, consistently with `view_fold`.

**FINDING 2026-09-13 -- `Op::PutChunk` replaces when it commits and unions when it replays, and one op is all that hides it.** Reached while implementing `merge_set`, which was going to be "`store_set` without the leading `DeleteKey`" until the tests said otherwise.

* **Live**: `Op::PutChunk` applies through `Memtable::put_chunk`, which **overwrites** the chunk's MVCC value.
* **WAL**: it logs as a bare `RecType::ChunkImage` -- key, then the chunk's ordinals, **no delete**.
* **Replay**: `apply_record` applies `ChunkImage` with a per-ordinal `insert`, which **unions** into whatever is underneath.

The two agree today only because the single producer, `WriteBatch::store_set`, emits `Op::DeleteKey` first, so both are unioning into an emptied key. **Drop that one op and a commit and its recovery differ** -- silently, and only after a crash. Demonstrated: removing the `DeleteKey` makes the committed state `[3, 4, 65536]` and the replayed state `[3, 4, 65536, 458752]`, an ordinal the commit had deleted returning from the log.

No test covered it, because every existing test either checkpoints before reopening or never reopens, and unioning into an *empty* key is indistinguishable from replacing it -- which is why the hole stayed open. `store_set_replays_to_what_it_committed` now pins it: it populates the key first, with ordinals the replacement does not contain, and fails on the sabotage.

`Op::to_record`'s own doc comment said `PutChunk` "logs as a **delete plus the chunk's ordinals**" -- describing the delete that would have made the two paths agree, and that is not in the code. That is the **third** wrong comment found this session, after `bitmap_mask`'s "without copying" and `Backing::Paged`'s "no leaf reports this yet", and the first one where the wrong comment was actively concealing a defect rather than merely being out of date. Both it and `apply.rs`'s `ChunkImage` comment ( which named `store_chunk`, a function that exists nowhere in the tree ) now state the divergence and warn against adding a `PutChunk` producer that omits the delete.


**CLOSING ADDENDUM 2026-09-19 -- `view_count` is declined, and the premise that carried it does not survive being checked.**

The amended prescription arrived as `.agents-workspace/tmp/view-count-prescription.md`, narrowed to `OrdSet::view_count` alone and re-specified as `Vec<OrdSet>` bit planes rather than a `Slice`, which removes the dependency on the withdrawn lens. It rests on one claim, stated as the thing that makes it immune to measurement: "not that a kernel would be faster, but that a capability is computed and thrown away".

**The capability is not thrown away. It is already reachable from the shipped public API**, in about fifteen lines and with no crate-internal access:

```rust
let mut planes: Vec<OrdSet> = Vec::new();
for i in 0..v.sets() {
    let mut carry = packed.view_select( v, i );        // public
    for p in planes.iter_mut() {
        if carry.is_empty() { break; }
        let next = p.and( &carry );                     // public
        *p = p.xor( &carry );                           // public
        carry = next;
    }
    if !carry.is_empty() { planes.push( carry ); }
}
```

A ripple-carry add of each constituent's indicator into an accumulator. Verified 2026-09-19 by a throwaway crate under `.agents-workspace/tmp/view-count-probe` with a path dependency on `yesno-core`: 8 constituents over a 200 000-ordinal span, both layouts, **154 285 logical ordinals' counts exact against a `BTreeMap` oracle built from the constituents**, and all three shipped `Reduce` variants reproduced from the planes -- `Any` as their union, `Parity` as plane zero, `All` as the support constrained plane by plane to agree with `sets`.

So what `view_fold` throws away is **one walk**, not the capability. That converts the ask into a ratio, which is the kind of claim that already retired the other three parts.

**The ratio, measured on a loaded machine so the spread is wide.** Downstream planes against a one-walk arm ( the arm written over the public `iter()`, so it is an upper bound on what a real `fold_interleaved`-shaped arm would cost, not a lower one ):

| layout | downstream planes | one `view_fold( Any )` | one-walk arm | what an in-crate arm buys |
|---|---|---|---|---|
| `Interleaved` | 6.1 - 23.1 ms | 1.0 - 2.1 ms | 1.3 - 2.8 ms | **4 - 8x** |
| `Blocked`, stride `2^20` | 0.11 - 0.21 ms | 0.03 - 0.08 ms | -- | **1x** |

**Under `Blocked` the premise is not merely weak, it is false.** `fold_via_select` never forms a count at all -- it folds with the pairwise kernels -- so for half the descriptor space there is nothing being computed and discarded, and an in-crate `view_count` would be character for character the loop above. The crate would ship an oracle arm that is exactly the code a caller can already write, a specialised arm, the differential test between them, and the module documentation, to buy 4 - 8x on one layout.

**Four findings, recorded because they outlive the decision:**

1. **The capability exists downstream today.** Above, with the construction, so it is re-derivable without the probe.
2. **`Blocked` has no count to discard.** The proposal's premise reads `fold.rs` and generalises from the `Interleaved` arm to the module.
3. **The refusal of `Reduce::Plane( j )` is correct, and for the right reason.** The enum is closed on *monoids*, not on return types; `Plane( j )` for `j > 0` cannot be folded pairwise without carrying, and `Parity` escapes only because XOR is a monoid that coincidentally equals plane zero. `fold_via_select` implementing all three through the tuned pairwise kernels is what makes that property load-bearing rather than decorative. This is the proposal's best paragraph and it argues **against** its own ask reaching the enum.
4. **`Vec<OrdSet>` has a data-dependent length, which the prescription does not address.** It promises `ceil( log2( sets + 1 ) )` planes; the natural construction returns however many the *data* needs -- one plane when no ordinal is held twice, whatever `sets` is. A caller indexing `planes[ 3 ]` is reading a length it did not choose. Padding with empty sets is the fix and it is a specification decision, so the shape is not as free of design as "no new type, no new vocabulary" suggests.

**The prescription named `view_reduce` and misattributed it, which is the sharpest thing in the whole exchange.** Its strongest section, "Your own use cases want it", says the facet histogram "today needs `Any` plus one `cardinality` per constituent, which is `n` walks for a quantity one walk already had". The first half is an exact description of `view_reduce( v, Cardinality )` and of its real cost -- the `n`-strided-filter path measured at 8.3x slow and 583 allocations in `view-reduce-along-the-logical-axis` below. The second half does not follow. **The two are the marginals of the same `n x W` matrix on opposite axes**: `view_count` is the column sums, one per logical ordinal; a facet count is the row sums, one per constituent. They coincide in exactly one place -- their grand totals, both `nnz`, verified as `sum_j 2^j * |plane_j| == sum_i |c_i| == packed.len()` at 3 660 -- and **neither determines the other**. Demonstrated by construction over two constituents on logical ordinals `{ 0, 1 }`: packing A ( `c_0 = {0}`, `c_1 = {1}` ) and packing B ( `c_0 = {0, 1}`, `c_1 = {}` ) have **identical** `view_count` of `[ 1, 1 ]` and facet counts of `[ 1, 1 ]` against `[ 2, 0 ]`. So `view_count` cannot answer a facet count at all, and the paragraph that was the proposal's best argument was an argument for a different operation. Note the same paragraph then switches axes again without saying so: "held by at least `t` of these constituents" is genuinely a column-axis question, so cohort overlap and facet counting -- consecutive sentences -- are on opposite marginals.

**And the use case and the ask point in different directions.** The README case the proposal invokes -- cohort overlap, "held by at least `t` of these" -- is answered by a threshold predicate in `fold_interleaved` at one walk and no allocation, which the prescription itself observes strictly dominates the planes, and then declines to ask for on the monoid principle. It is right to decline it on that principle. The consequence is that the operation the use case wants is not the operation being proposed.

**The decisive fact is simpler than any of the above: there is no caller.** The proposer states plainly that it is not blocked, does not consume it, and has its own bit-sliced accumulator. That is `yesno-core/src/stats.rs` again -- 1 600 lines gating one decision with zero callers anywhere in the workspace, deleted 2026-08-28, and the removal cost `lib.rs` and ARCHITECTURE's module diagram as well as the file. A `pub fn` here is an R1 / R6 / R7 semver promise for something nothing calls.

**What would reopen it**, in order of what each would settle:

* **A caller.** Any consumer that actually evaluates `view_count` on `Interleaved` data, with the workload. The 4 - 8x is real where the layout applies, and the objection is to unused API rather than to the operation.
* **A threshold predicate with a benchmark.** If cohort overlap is the case, `count >= t` in the interleaved arm is the cheaper answer and it is a smaller change than planes. It breaches the monoid closure, so it would need to be a method rather than a `Reduce` variant -- the same shape `view_count` would have taken.

**Why the kernel is the argument, and why it is a different argument from `view_count`.** `CHUNK_CARD` is 65 536 and a word is 64 bits, so when `n` divides 64 both are multiples of `n` and the bit phase within a word is `o % n` with no carry across words or chunks. General `n` needs `lcm( n, 64 ) / 64` words of masks, and a chunk phase of `chunk_base % n`, which is 0 whenever `n` divides 65 536. This is the `ops/bitmap.rs` fused-popcount family applied to a strided mask, and it is **not portable downstream**: `unstable_arrow::bitmap_words` reaches only bitmap containers and is the semver-exempt escape hatch, so arrays and runs have no public word view at all.

* **For.** 218x on a cell the module's own cost table already flags; a genuine structural gap rather than a derived convenience; a **fixed-size** return with no data-dependent length, which is what sank `view_count`'s `Vec<OrdSet>`; and it is the operation the faceted-search use case actually wants -- a facet histogram is per-constituent cardinality, not the per-ordinal count that was proposed for it.
* **Against.** **No caller**, which is the rule that declined `view_count` on the same day, and applying it to a consumer's proposal but not to our own would be the more expensive mistake. `Interleaved`-only, which is now a four-time pattern. And a real arm needs the array and run cases as well as the bitmap one, plus the `fold_via_select`-style oracle and the differential test between them.

**Naming, settled 2026-09-19: `Cardinality`, not `Popcount`.** The crate has answered this three ways already. `popcount` has never been a public identifier here -- 90 functions carry `cardinality` in the name against 7 carrying `popcount`, and all 7 are `pub(crate)` or private word-level bitmap helpers in `ops/bitmap.rs`. The two words are held apart on purpose: `codec.rs` rejects a "bitmap cardinality disagrees with popcount" and the test pinning it is named for their disagreement, so cardinality is the stated quantity and popcount is one way to compute it. And `Popcount` would be wrong for most of the implementation -- an array's cardinality is a slice length, a run's is a sum of interval widths, and the `Blocked` arm is `len_in_range`, none of which popcount anything. So a true in-crate scalar arm buys about **1.7x at high output density, ~1.0x at low**, plus all 94 allocations. **That is not the `ops::card` shape.** That module avoids a container *per chunk* inside the pairwise kernels and buys four zero-allocation queries from one `and_cardinality`; here the output is a single bulk sorted build at ~3 ns per ordinal, and the saving is proportional to output density and nothing else.

**Rank is the one with a real argument, and it is asymptotic rather than a ratio.** Under `Interleaved` the physical order **is** the logical order, so a counting walk can stop at `x * sets` instead of running to the end. `Reduce::Any`, same fixture:

| `x` ( fraction of span ) | `view_fold( .. ).rank( x )` | early-exit walk | speedup |
|---|---|---|---|
| 1 000 ( 0.5% ) | 1.799 ms | 0.013 ms | **142.7x** |
| 10 000 ( 5% ) | 1.743 ms | 0.104 ms | 16.8x |
| 50 000 ( 25% ) | 1.703 ms | 0.493 ms | 3.5x |
| 100 000 ( 50% ) | 1.710 ms | 0.963 ms | 1.8x |
| 200 000 ( 100% ) | 1.701 ms | 1.673 ms | 1.0x |

Linear in the fraction scanned, which is what an early exit predicts and is the evidence that it is one.

**And rank is genuinely not derivable today**, unlike `view_count`. The early exit needs a cheap restriction of the packed set to `[ 0, x * sets )`, and `OrdSet` has **no public range restriction**: `not_in_range` builds a complement, and `rank` / `len_in_range` / `range_summary` return counts rather than a set. So a caller cannot buy the 142x from outside the crate.

**If either is ever added, the shape is a logical window, not a rank.** Rank is `fold_in_range( 0, x ).len()`, and a window also serves pagination and range-restricted folds, so shipping `view_rank` would be shipping the special case and keeping the general one. `docs/formal-model.md` §14 Proposition 18 is the licence: a prefix-window restriction is a homomorphism of the whole Boolean signature and pushes down with no side condition, which is precisely the property a fold does **not** have and the module header is at pains to distinguish.

**Not added, for the rule that just declined `view_count`: there is no caller.** Applying that rule to a consumer's proposal and not to our own idea would be the more expensive mistake. The numbers above are the deliverable; the probe is disposable.

**A pattern worth checking first on any future `view/` ask: all three candidates so far pay on `Interleaved` and nothing on `Blocked`** -- `view_count`, popcount, and rank alike. It is structural rather than a coincidence of implementation. `Interleaved` is the layout in which physical order carries logical order, so it is the only one where a single walk can see a logical ordinal's entire story; under `Blocked` a constituent is a contiguous region, `fold_via_select` folds with the pairwise kernels and forms no per-ordinal count at any point. Note also that the `ops::card` identities are **two-operand**, so an n-ary cardinality cannot escape materializing the running accumulator -- `|A u B u C|` needs inclusion-exclusion -- and can save at most the final step.

  **The interaction with the read-path checksum cache is the sharpest, and it was introduced 2026-09-14.** `read_container_for` verifies a packed page with `verify_once( base, PAGE )` -- **one cache entry per page, covering the whole 4096 bytes**, because the stored CRC is a whole-page CRC. `write_at` evicts every verified region it intersects.   **Two further readings worth separating before anyone measures.** ( a ) *Writer-side*: the checkpoint gathers chunks from different keys into one `PackedPageBuilder`, which is a point where otherwise independent keys become order-dependent. ( b ) *Kernel-side*: two writes landing in the same 4096-byte page-cache page contend at page granularity whatever the engine does.

  **What is already known and constrains the hypotheses.** Pages are **built fresh** during checkpoint ( `PackedPageBuilder::new( PAGE )` ) rather than mutated in place, so I2 holds and a *live* published page is not rewritten under a reader. That makes ( b ) apply to freed-and-recycled cells rather than to live ones, and it is why the checksum cache is keyed on **file offset** rather than page id -- a recycled cell must invalidate, and an id-keyed entry would go stale silently.

  **The sharing itself is now pinned by two tests** ( `db::store::tests`, added 2026-09-15 ), so the mechanism is established even though its cost is not:
  * `one_packed_page_is_verified_once_for_every_key_it_holds` -- four distinct keys in one page produce **one** verified region, not four. Reddens if the cache key becomes per-chunk.
  * `a_write_into_a_packed_page_invalidates_it_for_every_key_in_it` -- a **content-preserving** write to the page drops that region, and a key that was never written then re-verifies the whole 4096 bytes. Reddens if invalidation is removed.

  The write is content-preserving deliberately: writing anything else corrupts the page, the re-read fails its checksum, and the assertion would pass on the *error* rather than on the re-verification. The fixture carries several keys per page because **a single-key fixture cannot express the amplification at all** -- with one chunk per page, "invalidate the page" and "invalidate that key" are the same event and the test would pass against an implementation with no sharing.

  **So what remains unmeasured is only the cost**, not the behaviour. Measure the consequence rather than reproducing the mechanism. The amplification predicts re-verification work proportional to keys-per-page, which `verified_count` churn and a CRC-cost differential would show directly; a single-key fixture cannot see any of it, so the measurement must vary **keys per page** and say so. -- *source: maintainer, 2026-09-15*

Resolve them first, outside `mem.write()`, then apply under the lock using the memtable where it has the chunk and the pre-read value where it does not -- the miss check is cheap and must stay under the lock, because a concurrent commit may have added the chunk in between. Safe because a published extent is immutable under I2, so a value read before the lock cannot go stale in a way that matters; it can only become *superseded*, and the memtable is already the authority for anything newer.

  Note the lock ordering was checked while measuring and is **consistent**: the only pair anywhere is `mem.write()` then `store.lock()`, inside `disk_chunk`. The checkpoint path drops the store lock before it takes `mem.write()`. No inversion, so this is a latency problem and not a deadlock one.

  The shape of the remaining fix is not obvious from the outside: the question is how long `mem.write()` is actually held per commit and whether the memtable can accept a commit without excluding readers for the whole of it. Do **not** carry over the assumption this backlog made about checkpoints -- that a lock a query touches repeatedly explains a shard-invariant total -- without re-deriving it here; the commit path has a different shape and its own control arm is `no writer`, which is cheap to run. The consumer has offered to measure whatever is pointed at on the commit path and says it is the number they now care about most. -- *source: consumer control arm, 2026-09-16*

  **The per-shard apply is parallel as of 2026-09-17, and it does not close this entry -- state the distinction before quoting it.** `WriteBatch::commit` now runs both the prefetch and the apply through the host-supplied `Dispatch`, one task per participating shard, so a commit spanning N shards overlaps N holds instead of serializing them. That shortens the **commit's** wall clock. It does **not** shorten the hold a reader waits behind: a reader on shard k still waits exactly as long for shard k's `mem.write()` as it did before, because that shard's critical section is unchanged. - [ ] **read-concurrency-is-bounded-by-shard-count** ( *2026-09-14, measured* ): `KeyStream::next_chunk` takes `Mutex<ShardStore>` **per chunk** and holds it across the whole of `read_container_for` -- trailer read, checksum verification, `buffer_at` and the decode.  
  ```text
    shards    1 thread    20 threads    scaling
         1     952.5        212.1        0.22x
         4     899.2        672.2        0.75x
        20     496.5       1743.6        3.51x
  ```

  Measured on 20 cores with one shared `Snapshot`, 3 776 reads per sweep. **At one shard it degrades rather than plateaus** -- 20 threads deliver a quarter of one thread's aggregate throughput. Note the knob has a cost: single-threaded is worse at 20 shards ( 496 against 952 ), so this is a tradeoff and not a free win.

  **Do not start by narrowing the critical section. That was this entry's first recommendation and the arithmetic contradicts it.** The section is **278 ns** ( 3.60 M reads/s single-threaded ). If one mutex merely *serialized* readers, 20 threads would still reach that 3.60 M. They reach **0.80 M** -- a **4.5x deficit beyond serialization**. So hold time is not the bottleneck; the overhead of contending for a short, hot lock is, and **shortening a section already too short only raises the acquisition rate**.

  The shard sweep corroborates it from the other side: at 20 shards the section is *longer* ( 533 ns ) and throughput is nonetheless **6.58 M reads/s**, because contention is spread over twenty mutexes instead of one. What pays is fewer contenders per lock, not a smaller lock.

  **The candidate is `RwLock<ShardStore>`, and it is smaller than it sounds.** All 13 shard-store lock sites were classified: **10 need only a shared borrow** -- every read path binds `let store = ...` and passes `&*store` ( `mod.rs` 172, 4053, 4117, 4138, 4201, 4290, 4337, 4511 and both `keystream.rs` sites 184, 314; `read_container_for` is itself `&self` ) -- and **3 need `&mut`**: `rebuild_allocator_at_open` ( 1248 ), `allocator().slab_count()` ( 2356 ) and checkpoint ( 2730 ), all open/stats/checkpoint paths, none on a query. So `.read()` at ten and `.write()` at three changes **nothing about when the lock is released** and needs no decision about holding it across the decode. Independently proposed by the consumer after the same elimination; unverified here.

  **But every measurement behind this entry is read-only with no writers**, including the consumer's, and that is the gap to close before converting anything. `RwLock` trades "readers serialize" for "**a writer may not acquire**", and the write side here is asymmetric in a way that matters:

  * `WriteBatch::commit` **never takes the store lock** -- it takes the memtable's `RwLock` and the WAL -- so the ordinary write path does not contend with reads at all.
  * **Checkpoint holds the store lock across its entire body** ( `mod.rs` 2730-2907: tree rebuild, superblock flip, deferred reclamation ). One long exclusive hold.

  `std::sync::RwLock` is not writer-preferring, and sustained full-occupancy reading is precisely the shape that starves a writer. **A starved checkpoint is not a latency problem**: checkpointing is what bounds WAL growth and what runs `reclaim_deferred`, so delaying it converts a throughput issue into a disk-space one -- a worse failure than the one being fixed. Measure a read/write mix, not only a read sweep, before believing any figure here.

  **A trap for anyone doing both halves: the inner `segs` / `pinned` / `verified` mutexes in `store/segment.rs` are redundant *only while the store lock is exclusive*.** `SegmentedMmap` is owned by value inside `ShardStore` and every production access is under `Mutex<ShardStore>`, so those three acquisitions per read currently guard against a race that cannot happen. Convert the store lock to `RwLock` and they immediately **become load-bearing**, because concurrent readers would then mutate `pinned` and `verified` at once. Removing them first and converting second gives data races on two `BTreeMap`s, and each step looks locally justified. See JOURNAL 2026-09-14.

  So the direction is reducing **acquisitions per read** or removing the shared mutex from the read path -- a read path that took `Mutex<ShardStore>` once per chunk plus three more inside `segment.rs` is acquiring four locks to move bytes that are already immutable under I2. Releasing the store lock before the decode remains sound ( the `Buffer` keeps its mapping alive independently, which is the whole purpose of `ExtentGuard` ) but is not by itself the fix.

  Do not start by converting locks in `store/segment.rs`. **The grid must be coarsenable, and that is where the performance is.** If positions are always single prefixes, ragged input costs a tree walk per chunk. If boundaries are instead the coarsest positions where *every* operand's classification is constant — the merge of all operands' run boundaries — uniform stretches advance in `O(1)` and cost is paid only at real transitions. Note what those boundaries are: they are the split/merge design's frozen cut set `X` ( the cut set `X` of `docs/formal-model.md` §6.3, generalized from span endpoints to run boundaries ), **discovered lazily by walking rather than computed and committed**. That removes that design's central problem outright — no committed partition, so no fusion write-back, no monotonicity hypothesis, no livelock, and forward motion is its own termination argument. The 1-filled absorption fires per position as `x ∩ Full = x` without being a rewrite rule.

**Interpretive overhead does not amortize here the way it does in a columnar engine.** There, per-tuple interpretation is spread over millions of rows; here a position is a chunk and there may be only hundreds, so walking the tree per position is a real cost. Flatten the tree once into a small stack machine and run that per position — in the design from the start, not retrofitted.

This is a second execution model, not a local change: `ChunkStream` is pull-based per-operator and an aligned evaluator is a different shape. They can coexist ( the evaluator is one `ChunkStream` at the root ), but it would subsume `segmented_or`, most of `concat_disjoint_or`, `segmented-and-with-shared-cursors`, the n-ary-operator direction, and most of the retired split/merge design. Prototype before committing. Its correctness argument is `docs/formal-model.md` §14, and **Prop 20 clause 2 is the trap**: this evaluator's boundaries are run boundaries, not prefix boundaries, so `Concat` is *not* a valid reassembly — two adjacent segments can contribute to the same chunk. Use the single-scratch-container append §14.3 describes.

  **This decides `statistics-earn-nothing`.** `ChunkProfile` already *is* per-operand `Empty` / `Full` / `Present` runs, so merging `k` of them yields the aligned segmentation directly. The statistics are not for gating rewrites — where they have measured as worthless three times — they are for driving the walk. Do not delete `ChunkProfile` or `PrefixOccupancy` until this is settled.

**Two prototype artifacts cost 3-20x before they were found, and both are the same mistake this codebase keeps making.** Binary-searching the run array per position, where the walk is strictly forward and wants a monotone cursor — the very thing `SetStream::seek` gallops for — cost 780 ns per segment on segments that do nothing.   **`prep` is the open question, and it is the `O(chunks)` term that has twice measured as not paying.** It is 5-15% of engine time on the winning rows but 13% of a 94 us query at sieve k=32, and it scales with total chunk count.   **Two consequences of dropping the grid, both improvements, both unmeasured.** ( 1 ) Boundaries become **demand-driven**: with no grid there is no classification array to build, each operand answers "next boundary at or after `p`" from a cursor, and cost is paid only for boundaries actually reached. That is where `prep` goes, and it dissolves the representation question below rather than answering it — there is nothing to precompute. ( 2 ) **The prototype cuts each segment at the minimum boundary over *all* operands, including ones whose classification did not determine the answer.** On `( B ∪ C ) ∩ A`, `C` has 1000 chunks contributing boundaries throughout `[0,99]` where `A` is `Empty` and the result is `Empty` regardless. The segment should extend to the next boundary among the operands that **decided** the answer — `A` alone, there. That is the maintainer's earlier "ruling sets" idea recovered per segment and dynamically rather than globally and statically, and it is the eliminator idea from the k-way literature one level up. It is also what makes demand-driven boundaries pay: `C` is never asked for a boundary in a region `A` has already settled.

  Predictions worth testing together, since ( 2 ) is what makes ( 1 ) worth having: `prep` collapses toward zero on operands with few boundaries ( `A` ) and does **not** collapse on operands whose classification alternates every few prefixes ( `sieve`, ~200 boundaries per operand ) — there the work moves from `prep` into the walk and the total is roughly unchanged. So the predicted gain is concentrated exactly where the model already wins, which is a reason to be suspicious of it and to measure rather than assume.
