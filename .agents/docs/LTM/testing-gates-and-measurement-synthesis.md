# Testing, Gates, and Measurement Synthesis

## Summary

The project relies on deliberately independent test layers. Properties, external format oracles, expression equivalence, allocation counts, operational scenarios, PostgreSQL regression fixtures, and language-client tests catch different failure classes and must not be collapsed into one apparently comprehensive suite. Measurements are evidence only when their construction, corpus, repetition method, and independent oracle are recorded.

## Stable Knowledge

- The generic kernel and `BTreeSet<u64>` properties are semantic oracles; the `roaring` dev-dependency is both a semantic and byte-format oracle; eager `OrdSet` evaluation is the lazy expression oracle; allocation counters guard non-materializing paths. Each is intentionally independent of the implementation it checks.
- Boundary-biased generators are load-bearing. Uniform random `u64` values almost never exercise dense arrays, run promotion, container boundaries, or representation hysteresis.
- Expected output generated by the system under test is not an independent omission oracle. Tests for inventories, manifests, routing, or replicated objects need a separately constructed expected set or count that fails when an item is silently skipped.
- Multi-session behavior must use real independently connected sessions with deterministic marker synchronization. Sequential commands on one connection cannot prove transaction visibility, blocking, cancellation, or snapshot isolation.
- Network timing loops belong in the host when reporting nanoseconds. A loop interpreted by the Python harness measures host-call overhead and `monty`, so Python-side walks should report work counters instead of wall-clock latency.
- The routine Rust gate includes workspace Clippy with warnings denied, formatting checks, and the core tests. The cargo gate and PostgreSQL Bazel gate are both authoritative and neither subsumes the other; Python and Java client surfaces have their own gates as well.
- Miri is not part of the current automatic deep gate. The former Miri path was removed when it could no longer provide reliable signal for the supported toolchain and dependencies; any manual Miri experiment must be reported as such rather than implied to be enforced.
- Fuzzing protects total decode behavior: arbitrary input must return an error or a valid container and must never panic. Sanitizers or other dynamic tools complement this, but do not replace the deterministic gates.
- Performance claims require the corpus construction, terminal condition, warm-up policy, repetition count, distinct-pair count, and observed dispersion. One repeatedly timed pair is not a workload distribution.
- Allocation budgets are behavioral contracts, not tunable targets. A red budget means the implementation materialized or retained more than its design permits; raising the budget would erase the oracle.
- A cloud cleanup assertion against a resource filter needs a positive observation while the resource exists. Requiring zero only after cleanup is vacuous when the filter never matched.
- Billable cloud verbs require an explicit gate opt-in, and arm selectors reject unknown or contradictory values. Local emulation, native filesystems, and real AWS are complementary evidence, not interchangeable substitutes.
- Process-wide counters such as `/proc/self/io` need a dedicated test process. Repetition and minimum selection cannot remove continuous interference from neighbouring tests.
- The retained all-in-one E2E image keeps artifact builds and toolchains aligned across containerized gates, while gates select their own fixtures and entry identity. The real-AWS runner remains separate because shipping the full artifact tree to each billable host would be wasteful.
- A release workflow must gate before publishing and verify each architecture of the final manifest. A successful multi-platform build does not prove that each manifest entry contains binaries for its declared architecture.
- Local and remote lint toolchains must be named explicitly. The repository default can pass while CI's newer `stable` emits a lint that does not exist locally; `cargo +stable clippy --workspace --all-targets --all-features -- -D warnings` is the faithful reproduction of that CI surface.
- AddressSanitizer runs library and integration-test targets with `--lib --tests`. Sanitizer-instrumented doctests cannot link reliably against dependency rlibs built without the sanitizer runtime, and deleting doctests is not a repair.
- Reusable workflow composition is itself a remote test surface. A called workflow must own a literal concurrency namespace because `github.workflow` resolves to the caller's name and can otherwise make the callee cancel the run waiting for it.

## Operational Guidance

- Choose the test layer that is structurally capable of catching the failure: semantic property, roaring differential, expression equivalence, allocation budget, operational scenario, SQL regression, or language-client integration.
- For a newly fixed bug reachable through `OrdSet` or `ChunkStream`, add coverage to an oracle or property layer before considering a narrow unit test sufficient.
- Build expected inventories independently from persisted or streamed output. Prefer explicit IDs, independently counted source records, or a second implementation with different failure modes.
- Coordinate concurrent tests with explicit barriers or markers, bounded waits, and cleanup paths. Do not depend on scheduler timing or sleeps.
- Record measurements in LTM with enough construction detail to rerun them; discard one-off instruments after the finding is captured.
- Run every gate implicated by the touched surface and report each result separately. Passing cargo does not imply the ABI-pinned PostgreSQL build passes.
- Make observers outlive the component timeout they diagnose, reserve output for warnings and identifiers, disclose truncation, and collect state before cleanup removes it.
- For cloud cleanup, first observe a nonzero owned resource set, then require zero after cleanup. Preserve Terraform state and remote evidence until the failure path has reported them.
- Isolate exact process-wide counters in their own integration target rather than filtering or statistically compensating for unrelated work.
- Validate triggers, reusable-workflow contexts, concurrency, actions, caches, and runner capabilities through the actual remote event path. Nested `gate / <job>` entries prove that the call expanded; only a complete green graph proves the workflow.

- `yesno-core/tests/differential.rs` owns roaring semantic and byte-level format identity.
- `yesno-core/tests/expr_equivalence.rs` owns lazy-versus-eager equivalence and cardinality agreement.
- `yesno-core/tests/allocation.rs` owns non-materialization and allocation budgets.
- `e2e/scenarios/` owns operational sequences and maintained measurement fixtures.
- `e2e/postgresql/sql/` and `e2e/postgresql/expected/` own PostgreSQL behavior under the Bazel-built server ABI.
- `scripts/gate.sh`, `scripts/gate-pg.sh`, and repository-specific client gates are separate authorities.
- `.github/workflows/ci.yml` and `.github/workflows/release.yml` own remote trigger, reusable-call, concurrency, and publish ordering.
- `.agents/docs/QUALITY_GATE.md` and `.agents/docs/TESTING.md` own the current procedural detail.

## Tests

- Routine Rust changes run `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo fmt --check`, and `cargo test -p yesno-core`; the full repository gate adds its documented checks. `--workspace` is not optional — a bare `cargo clippy` lints `default-members` ( `yesno-core`, `yesno-arrow` ) and silently skips the other six crates.
- PostgreSQL-affecting changes also run `./scripts/gate-pg.sh`; expected SQL output is regenerated only after its diff is understood.
- End-to-end scenarios run through `cargo run -p yesno-e2e -- <scenario>` and use `--show-output` when inspecting a passing measurement fixture.
- Decode changes retain the `deserialize_never_panics` property and the fuzz contract.
- Documentation checks include the layout diagram and self-contained `docs/` invariants.
- Client changes run their language-native suites with the supported pinned toolchain.
- Real-AWS arms run through `./scripts/gate-aws.sh` with explicit opt-in; partial arm results are reported as partial until one invocation proves the shared stack and cleanup compose.
- Release validation inspects both `linux/amd64` and `linux/arm64` manifest entries and executes the shipped binaries under the matching platform, in addition to local Dockerfile and workflow checks.
- CI lint parity is checked with the toolchain CI names, and the ASan step is scoped to `--lib --tests`. Remote workflow validation must observe the complete nested job graph rather than infer success from local equivalents or a scheduled badge.

## Pitfalls

- Reusing the implementation's inventory or serialization logic to construct expected results makes omissions invisible.
- A single hand-written unit test rarely protects a boundary-sensitive representation or planner invariant.
- One-session SQL scripts cannot demonstrate cross-session visibility or blocking.
- Timing Python loops and reporting nanoseconds measures the harness rather than the kernel.
- Treating Miri as an automatic gate overstates current coverage.
- Passing one gate does not authorize skipping another gate that builds a different ABI, feature set, or client surface.
- Loosening an oracle, property, expected file, or allocation budget to make a failure disappear destroys the reason that test layer exists.
- Do not let a harness deadline expire before the component's own diagnostic timeout.
- Do not collect post-mortem evidence after cleanup or compress known resource identifiers and error tails into a count.
- Do not treat a minimum process-wide counter as isolated evidence or a single loaded-machine timing as a stable cost.
- Do not infer per-platform binary identity from a successful multi-platform manifest build.
- Do not derive reusable-workflow concurrency from `github.workflow`; the caller controls that context.
- Do not report CI fixed from locally green equivalents or the presence of nested jobs alone; the remote graph must finish successfully.
